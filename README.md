# 云计算产品需求洞察与竞品对标引擎

> 输入客户原始诉求，输出**需求说明书**（每个需求点可追溯到原文）、
> **IaaS/PaaS/DAAS/MASS/SaaS 五层产品竞品对标矩阵**（四家厂商）、
> **周/月度数据分析报告**、**技术交流材料**（支持打单）与**代码生成的流程图**。
>
> **客户场景为自拟、非真实业务数据；产品数据为各厂商公开产品资料。**

零第三方依赖，`git clone` 后直接跑。

---

## 1. 为什么做这个

产品经理的核心瓶颈不在「写文档」，而在**把杂乱诉求变成可执行需求**，以及
**对竞品有基本认知**。这两个环节的共同问题是：

| 常见做法 | 问题 |
|---|---|
| 需求单靠手写 | 同一诉求在不同渠道表述不一致，漏项无法发现 |
| 竞品分析靠印象 | 「华为云很强」但说不出强在哪一层、哪个能力域 |
| 流程图手工画 | 需求一变图就过期，看不出改了什么 |
| 竞品表带主观打分 | 客户一问「依据是什么」就答不上来 |

这个工具做的事：**把需求与竞品认知都变成可复算、可追溯、可版本管理的产物。**

## 2. 覆盖哪些能力

| 能力 | 对应 JD 职责 | 输出 |
|---|---|---|
| 客户需求结构化 | 职责 1 · 收集整理统计分析产品需求 | 需求点清单，**每个带原文出处** |
| 需求说明书 | 职责 2 · 需求说明书 | 7 章草稿 + 字段完整率 |
| 竞品对标矩阵 | 职责 5 · 主流云厂商认知 | 四厂商 × 五层 × 能力域，含**空白项** |
| 周/月数据报告 | 职责 4 · Excel/BI 监控产品数据 | 7 项 KPI + 需求类型分布 |
| 技术交流材料 | **职责 6 · 支持售前及销售、技术交流、打单** | 诉求↔能力映射 + 实施路径 |
| 流程图/原型图 | 任职 4 · Axure/XMind（**代码生成替代**） | Mermaid 文本，可版本 diff |

## 3. 核心设计决策

### 3.1 需求点必须可追溯到原文

每条需求点记录命中的**原文片段与字符位置**。写不出出处的需求点是编的。

实测（`REQ-2026-001`）：

| 编号 | 类型 | 原文依据 |
|---|---|---|
| RP-01 | 作业调度效率 | 「排队」 |
| RP-02 | 合规与数据驻留 | 「机房」「不上公有云」 |
| RP-03 | 竞品认知 | 「华为」「阿里」「对标」 |
| RP-04 | 资源迁移纳管 | 「放到云上」「统一管」 |
| RP-05 | 运维管理效率 | 「运维」「管理麻烦」 |

### 3.2 空白项是输出的一半价值

竞品对标不只是知道对方有什么，**同样是知道对方没什么**。

实测覆盖情况（四厂商 × 五层 = 20 格）：

| 指标 | 值 |
|---|---|
| 产品条目 | 44 条 |
| 厂商覆盖率 | 100%（4/4） |
| 层覆盖率 | 80%（4/5） |
| 能力域覆盖率 | 100%（11/11） |
| **空白项** | **9 格** |

9 格空白中最值得注意的是**曙光云的 SaaS 产品线未查到公开信息**，
以及华为云 / 阿里云 / 腾讯云在 MASS（异构算力即服务）层的空白。

> 这些空白**不推测填充**。技术交流时的正确做法是明确告知客户
> 「该层暂无可查的公开信息」，而不是含糊带过或编一个。
> **在 4.52% 毛利行业里，数据诚信本身就是竞争力。**

### 3.3 不做优劣评分 —— 这是对 JD 的准确理解

JD 原文是「对主流云计算厂商基础产品的**认知**有加分」。

这是**认知**要求，不是**评判**要求。所以本项目：

| 做 | 不做 |
|---|---|
| 并列各厂商在五层上的客观产品线 | 打分、排名、推荐序 |
| 每条注明来源与抓取日期 | 收录价格与 SLA 数字 |
| 显式列出空白项 | 推测对方未公开的能力 |

`tests/test_competitor_report.py` 用两个测试强制这一纪律
（扫数据字段、排除纪律声明本身 —— 声明里必然出现「不做优劣评分」这些词）。

### 3.4 流程图用代码生成，替代 Axure/XMind

| | Axure / XMind | 代码生成（本项目） |
|---|---|---|
| 版本管理 | 导出图片/文档，**无法 diff** | 纯文本，**git 可 diff** |
| 需求变更 | 手工改，易漏 | 改模板即全图同步 |
| 批量出图 | 逐张手工 | 参数化循环 |
| 交付形态 | 图片附件 | 文本，可直接进 Wiki |

Axure 的价值在**交互原型**。而 JD 要的是「原型**或流程图**」——
流程图用代码生成是更合适的形态，因为流程会随需求变，文本 diff 能看到改了什么。

输出为 **Mermaid 文本**：可直接粘贴进 GitHub / GitLab / Notion 渲染。

## 5. 方法

```
data/requests/raw_requests.json ─┐
data/products/*.csv ─────────────┼─> catalog.py ──> 目录（缺列即报错，空字段=None）
                                 │
   requirement_builder.py ────────┤ 原始诉求 → 需求点（带原文出处）→ 需求说明书
      │                          │
      ├─ competitor_matrix.py ───┘ 四厂商 × 五层 × 能力域 + 空白项
      ├─ prototype_helper.py ────── 代码生成需求流转图 + 能力域结构图
      ├─ report_builder.py ─────── 周/月报 KPI
      │
      └─ doc_assembler.py ──────── 需求说明书 / 竞品报告 / 技术交流材料 / 周月报
```

## 6. 快速开始

环境：Python 3.10+（验证于 3.12.8 / Windows）。**无需安装任何运行时依赖。**

```bash
# 跑全流程
python -m src.cli

# 只出竞品对标报告
python -m src.cli --competitor

# 指定报告周期
python -m src.cli --period 月报

# 跑测试
pip install pytest
python -m pytest -q
```

输出落在 `output/`：

| 文件 | 内容 |
|---|---|
| `prd_draft.md` | 需求说明书：需求信息 / 场景 / 需求点（含原文出处）/ 约束 / 完整度 / 流程图 / 待明确事项 |
| `competitor_report.md` | 竞品对标：覆盖度 / 五层矩阵 / 能力域对照 / 结构图 / **空白项清单** |
| `tech_talk.md` | 技术交流材料：客户状况 / 诉求↔能力映射 / 对标要点 / 实施路径 |
| `weekly_report.md` | 周月报：KPI / 类型分布 / 待补充字段 / 竞品快照 |
| `competitor_matrix.csv` | 矩阵明细，可直接贴进 Excel 做二次分析 |
| `result.json` | 全量结构化结果 |

## 7. 实测输出

```text
$ python -m pytest -q
.................................................                        [100%]
49 passed in 0.47s

$ python -m src.cli
需求 1 条 ｜ 需求点 5 个 ｜ 平均完整率 67%
竞品矩阵：产品 44 条 ｜ 厂商覆盖 100% ｜ 层覆盖 80% ｜ 能力域覆盖 100%
空白项 9 格（未查到公开产品的厂商×层组合）
```

**「层覆盖率 80%」是一个真实且有意义的数字**：五层里有 4 层有产品条目，
MASS（异构算力即服务）在三家公有云厂商处均未查到 —— 这恰好是**曙光的差异化位置**。

字段完整率 67% 也是真实值：6 个必填字段里 4 个有内容，
`优先级` 与 `期望指标` 标为待补充 —— 因为**客户原文没给，不能编**。

## 8. 已知局限

| # | 局限 | 影响 | 补齐方式 |
|---|---|---|---|
| 1 | **样本需求只有 1 条** | 类型分布与完整率的统计意义有限 | 接入真实需求工单后重跑 |
| 2 | **曙光产品线为 secondary 级** | 官网未公开完整 SKU 清单 | 以厂商正式产品手册为准 |
| 3 | **腾讯云标 secondary** | 未逐条核对官方规格书 | 逐条核对后升级 |
| 4 | 平均澄清轮次为占位值 | 无法度量需求返工率 | 需真实工单记录 |
| 5 | Mermaid 只能画流程图 | **做不了交互原型** | 真需要时补 Axure |
| 6 | 不含价格与 SLA | 无法做商业对标 | 属商业条款，本就不该公开 |
| 7 | 无业务数据 | **不做营收或用户增长预测** | 接入产品运营数据后可扩展 |

第 1、4 条决定了这个工具当前的定位：**它验证的是「需求与竞品认知的工程化方法」，
不是「产品经理的实际工作成果」。** 真实需求工单与产品运营数据需要入职后补齐。
